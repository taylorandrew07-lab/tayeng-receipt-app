## Spine: **Design A — The Close-Out Ledger**

C scores highest and A is still the spine. Stating that plainly: C wins on execution, A wins on model, and the model is the part you cannot graft cheaply.

The deciding fact is that C's success metric is unattainable on this dataset. C's premise is "until the board is empty," but its right panel is 43 orphan receipts of which 27 will never pair with anything, and C provides no way to close a receipt — so the board is permanently non-empty and the psychological mechanism it is built on never fires. C's fix for that is A's receipt-side closure columns. Since you must graft A's model into C regardless, spine on the model and graft C's surface — which is genuinely separable, being one client component plus one server action, and which A already scopes as `/reconcile/board`.

A also matches the sentence Andrew said. "Cross off every single thing off the list" is an open-item count driven to zero with a stated reason per removal, not a board that pairs.

## What all three missed

1. **Every "exact match" affordance in all three designs is structurally unreachable for the 16 USD receipts.** `receipts.ttd_amount` is derived from a single scalar `user_settings.usd_to_ttd_rate` (`0001_initial_schema.sql:66`, default 6.8) while the bank applies its own rate on the day — the brief measures a consistent ~0.45% gap. All three specify an exact-amount pre-pass and an EXACT pill at absolute tolerance (<0.005 / 0.01), which by construction can never fire for a USD receipt, and C's phone flow then dims everything non-exact to 40% — so every USD receipt is permanently in the dimmed tier. `amountScore` at `match.ts:47-53` is already percentage-based so scoring half-works, but the pre-pass, the pill and the ring are all absolute. Exactness must be currency-aware (`|diff| <= 0.01` same-currency, `<= 0.75%` cross-currency; C mentions this once in its drag section and nowhere in its scoring), and every confirmed USD match should write back the implied observed rate.

2. **The unbuilt delete guard becomes actively dangerous the moment a persistent count goes on screen, and none of the three makes it a prerequisite.** `0016_match_durability.sql:31-36` changed `statement_transaction_id` to `ON DELETE SET NULL`, yet `lib/statements/actions.ts:20` still carries the comment "matches cascade-delete via FK" — false since 0016 — and discards `{ error }` on both the storage `remove()` and the `delete()`. Under all three designs the ledger becomes the system of record, so deleting a statement silently strands rows and the open count moves with no explanation. Any design that puts a number on screen must guarantee the number only changes for a stated reason. Step 11 is a hard prerequisite, not a later step.

3. **Two statements parsed with `period_start IS NULL` and no design surfaces it.** `statement_coverage` (`0014:51-67`) recovers coverage by coalescing to min/max `txn_date`, so the data is fine — but A and C both print a period on the close-out PDF derived from that view without flagging that it is *inferred*. A report header reading "1 Apr – 30 Apr" when the parser never read a period is worse than one reading "dates inferred from transactions."

4. **Nothing defines completeness against the paper statement, and all three make the count more prominent without making it more trustworthy.** `TxnSchema` (`lib/extraction/parse-statement.ts:7-16`) carries no raw line text and no per-line confidence, `statement_transactions` has no `raw_extraction` equivalent (unlike `receipts`, `0001:147`), and `app/api/statements/parse/route.ts:130` returns `{ok:true, count:0}` on a zero-transaction parse which the uploader renders as a green badge. So "everything crossed off" can mean "the parser found 12 of 34 lines and you crossed off all 12." Minimum fix: capture the statement's printed total-purchases figure as one number at parse time and show "lines total TTD X of statement total TTD Y" in the ledger header. That single number is the only real check that exists.

5. **The largest pot of money in the dataset has no button on it.** 27 unsent orphan receipts, TTD 11,648.69. `receipts.sent` is written by `setReceiptsSent` (`lib/receipts/actions.ts:259-268`), which revalidates only `/receipts`. A treats `sent` as a close reason and B and C show it as a state, but none of the three puts a bulk "send these to the accountant" action on the reconciliation surface — so the single highest-value move Andrew can make requires leaving the close-out screen and going to a different page.

6. **All three write vendor aliases keyed on the normalised statement description, and none warns off the adjacent footgun.** `charge_key_of` (`0015:23-30`) puts the raw normalised description into `charges.charge_key` and `assign_charge` (`0015:94-110`) merges on exact key equality. Once aliasing exists, the obvious "improvement" is to key charges on the alias — which would merge two genuinely different purchases at `STAR PETROL 112 ROBERTS S` and `STAR PETROL 45 EASTERN M` into one charge and silently delete real work, defeating Guard 1. The plan needs an explicit "aliases affect scoring only; do not touch `charge_key_of`." Related and also unnoted: all three add rule types to `learning_rules` while the only read path, `app/api/receipts/extract/route.ts:121`, is an unfiltered, unpaginated `select("*")` — adding `vendor_alias` and `noise_pattern` rows makes that query strictly worse. Filter by `rule_type` before adding to it.
